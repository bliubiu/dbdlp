# ADR-004：语义类敏感数据（人名/地址/公司名）内容级识别方案

- 状态：Proposed（提议中，待评审）
- 日期：2026-11-15
- 关联：AGENTS.md 项目功能（内置规则含人名/地址/公司名）、docs/02 §14.3/§14.4（风险分级与置信度）、docs/07 §3.6（语义类强制人工复核 SEM-01）、M3「语义识别增强（需新 ADR）」

## 背景与问题

AGENTS.md 内置敏感数据清单包含**人名、地址、公司名**三类语义数据。当前实现仅有两条路径覆盖它们：

1. `columnNameHints` 元数据辅助：列名/注释含「姓名/地址/公司」等关键词时给该列弱命中类型——**列级提示，与内容无关**；
2. 内容级识别为零：示例数据（`T_DBDLP_TEST_CUSTOMER.CUST_NAME` 等）扫描时无任何内容命中。

基线评测（docs/12）确认语义类内容识别为零覆盖，但语义类在三处场景有真实需求：台账 completeness（语义列不出现在报告中）、风险分级（`hasMeta` 分支形同虚设）、整改建议针对性。

语义识别的固有难点：中文人名/地址/公司名无可靠结构性特征，正则召回与误报强负相关；误报直接进入台账扰动词表与复核队列。

## 决策驱动因素

- docs/07 §3.6：语义类置信度**最高「中」且必须进人工复核**（SEM-01），不可自动判高风险——误报代价被复核流程兜底，但复核队列容量有限，仍需控制误报率；
- 引擎形态：四层流水线（字节扫描→正则→校验器→自定义）已稳定，语义识别需以**第五类规则形态**接入而非旁路；
- M3 判据：「语义识别增强（需新 ADR）」——本 ADR 即前置条件；
- 样本现实：语义类无结构化样本集（openDLP 仅 PERSON/COMPANY_NAME/LOCATION 列数据可作参考语料）。

## 考虑的选项

### A. 词典＋结构规则内置（推荐）

- **人名**：中文姓氏表（约 500 常见姓＋复姓）＋ 1~2 字名（合计 2~4 汉字），叠加上下文信号（同批值离散度高、与称呼后缀「先生/女士/经理」共现）；
- **公司名**：后缀词典（有限公司/股份/集团/合伙/工作室等）＋ 前缀地名可选——后缀命中即候选；
- **地址**：行政区划词表（省/市/区县/路/街/巷/号/栋/室）结构匹配，要求 ≥2 级行政区划词共现（对齐 docs/07 RS-09「行政区划层级一致」）；
- 接入方式：引擎新增 `dictionary` 规则形态（词典以嵌入资源随版本发布，可 YAML 覆盖扩展）；
- 置信度固定「中」、风险 `medium`（`hasMeta` 分支已有），强制 `pending_review` 复核。

### B. 引入 NLP/ML 模型

- 召回/精度最优，但违反项目零外部依赖与单二进制约束（CGO/模型文件），推理延迟影响流式扫描；本期否决，远期若精度不达标再评估。

### C. 维持仅列名辅助

- 零成本，但内容级覆盖为零，台账对语义数据不可见；与 AGENTS.md 内置清单承诺不符。

## 决策

**采用选项 A**（词典＋结构规则内置），分期实施：

1. 第一期：公司名后缀规则＋地址行政区划结构规则（误报可控、结构特征强）；
2. 第二期：人名姓氏词典（误报敏感度高，需配合白名单词表——通用词「北京市」「有限公司」等不得判为人名）；
3. 全部语义命中：置信度「中」、风险 `medium`、`ReviewStatus=pending_review` 强制复核；基线评测（docs/12）语义类单列（EV-02「语义类单列」），样本集从 openDLP 的 PERSON/COMPANY_NAME/LOCATION 列构建。

## 后果

- 正面：语义类台账可见性从零到有；复核流程获得真实输入；与 AGENTS.md 内置清单对齐。
- 负面/风险：词典维护成本（姓氏/区划/后缀表随版本演进）；人名误报需白名单治理；引擎新增 dictionary 规则形态需要字节扫描兼容（中文无字节前缀特征，bytescan 需支持跳过或按 UTF-8 首字节范围过滤）。
- 中性：不改变现有 13 类结构化规则的任何行为。

## 验证

- 实施前：语义类样本集（openDLP PERSON/COMPANY_NAME/LOCATION，每类 ≥200）进 `testdata/baseline/`；
- 实施后：基线评测增加语义类三行（精度优先口径：precision ≥90%，召回不设硬阈值，单列记录）；
- 每批语义命中抽检人工复核误报率，连续两批 >20% 则回退该词典条目。
