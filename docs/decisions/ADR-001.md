# ADR-001: 识别引擎自研而非内嵌 GoDLP

## Status

Accepted（2026-11-13）

## Background

v1.0 架构文档采用「A 路线：GoDLP 识别内核 + 自研采集层」，把 `bytedance/godlp` 作为内嵌识别内核。该路线与总纲 `AGENTS.md` 冲突，且接口描述未经核实：

- 总纲第 39~44 行要求规则分层为「字节扫描器 → 正则规则 → 校验规则 → 自定义 YAML 规则」，并列出身份证校验位、银行卡 Luhn、邮箱校验等自研校验器。
- 总纲第 22 行只写「敏感识别引擎，正则 + 校验器 **参考 godlp 项目实现**」，措辞是参考而非内嵌。
- 总纲第 241 行明确「识别敏感字段可使用字节扫描，**避免使用低效的正则匹配规则**」，与 godlp 对每个输入值跑全量检测器不同。
- 联网核实：godlp `Close()` 真实签名**无返回值**（`func (I *Engine) Close()`），而 v1.0 文档写成 `Close() error`，印证「接口描述未经核实」；若按此施工属幻觉接口失效模式。
- godlp 内置规则面向字节业务日志，与国内证件／信创字段盘点所需的自定义规则、版本快照、掩码策略不天然对齐。

## Decision

**本项目自研分层识别引擎，不 import、不 `go get`、不链接 `bytedance/godlp`，不调用其任何 API，不复用其内置规则文件。** godlp 仅作设计参考（三段式 `Detect → Filter → Verify` 流水线与规则分段组织思路）。

自研四层流水线（架构文档第 6 章）：

1. **字节扫描器**：以字符特征（连续数字长度、`@` 字节、校验位、分隔符、企业前缀）做廉价前置筛选，仅候选片段进入后续层，避免每值跑全量正则。
2. **正则规则**：按敏感类型注册编译后的正则，仅对候选片段匹配，高召回。
3. **校验规则**：注册式 `Verifier`，实现身份证校验位、银行卡 Luhn、邮箱、号段、统一社会信用代码校验位；通过提升置信度，未通过标记「仅格式命中」进待复核。
4. **自定义 YAML 规则**：企业内部证件号、工号、合同号，与内置规则同构、按 `rule_id` 去重合并。

配套决策：

- 规则集中于 `configs/rules.yaml`，含 `version` / `globals` / `rules` 三段，加载时校验版本、ID 唯一、正则可编译、校验器已注册，任一失败任务拒绝启动。
- 任务启动生成 `rule_version` 并写 `rule_snapshot` 表，历史报告可复现。
- 引擎端口 `Engine` 定义于 `domain/port`，实现位于 `infrastructure/engine`；接口 `DetectValue` / `DetectRow` / `RuleVersion` / `Close`，`Hit` **不含明文原值**，只含掩码值。
- 本期不使用 godlp 脱敏链路，也不使用 NER 模型；人名／地址／公司名仅由字段名／注释与自定义规则辅助判断，标注「待增强」。

选型对比（架构文档 2.2，加权）：内嵌 godlp 16、自研分层 24、纯正则无字节扫描 20 → 锁定自研分层。

## Consequences

**正面**

- 与总纲四层规则分层、字节扫描优先、中文校验器清单完全对齐。
- 消除幻觉接口风险：不再依赖签名未经核实且 `Close()` 已被证伪的外部 SDK。
- 规则格式、输出结构、脱敏策略、版本快照全部自控，支撑企业自定义规则与合规留痕。
- 少一第三方依赖，单二进制离线构建与信创部署更简单；规则随包发布，运行时不依赖外网。
- 字节扫描前置过滤降低大批量采样值上的 CPU 开销。

**负面 / 成本**

- 需自研维护正则、校验器、字节特征与正负样本集，工作量高于调用 SDK；TDD 硬要求，每校验器必备正负用例。
- MVP 阶段规则数可能低于成熟 SDK 开箱水平，靠可配置 + 自定义 YAML + 误报复核回流补齐；本期不做 NER，人名／地址／公司名识别弱于含模型方案，已列入 out-of-scope 与扩展点。

**风险与护栏**

- 规则正则必须编译校验；禁用规则只不参与识别，不删除定义。
- `Hit.RawValue` 类字段一律禁止；`Candidate.Raw` 仅引擎内瞬时，用后即弃。
- 后续若引入外部识别能力，须新开 ADR 并先完成接口存在性核验，不回退到「凭印象写签名」。
